## 0. 本文的立场

这个项目的出发点从一开始就是**实验**，不是产品。性能只是实验中**可能**探究的方向之一。

因此本文的组织方式是：

1. 先把**参考实现的事实**摆清楚（有 `file:line` 依据，标注可证实 / 推断）
2. 再明确 **26.2 与参考实现所处的时代差异**——这是决定"能不能照搬"的根本
3. 然后给出**唯一的、确证的平台级杠杆**：Java 25 的 Project Panama
4. 最后落到**方案大纲**：分层、阶段、每层的开放问题

一个必须写在前面的结论：**"换 API 能提升光追性能"这个命题，经本次调查后被否证**（见 §4）。继续走 D3D12 的正当理由是**实验价值 + 平台整合 + 工具链**，而非帧率。

> 许可约束已解除（使用者已确认许可证不是问题），本文不讨论许可对方案选择的影响。

## 2. 时代差异：为什么 Radiance 的集成层在 26.2 上不能照搬

Radiance 用 **60+ 个 mixin** 深勾 Minecraft 的渲染内部。用本仓库 `docs/official-262/` 的官方源码逐类核对结果：

| Radiance 的挂点类 | 在 MC 26.2 | 26.2 的实际替代者 |
|---|---|---|
| `WorldRenderer` | 不存在 | `LevelRenderer` |
| `ChunkBuilder` | 不存在 | `SectionRenderDispatcher` |
| `SectionBuilder` | 不存在 | `SectionRenderDispatcher` |
| `BufferRenderer` | 不存在 | `GpuBuffer` + `CommandEncoder` |
| `BufferAllocator` | 不存在 | 同上 |
| `BuiltBuffer` | 不存在 | 同上 |
| `ShaderProgram` | 不存在 | `RenderPipeline` |
| `RenderPhase` | 不存在 | `RenderPipeline` |
| `CompiledShader` | 不存在 | `RenderPipeline` |
| `LightmapTextureManager` | 不存在 | `Lightmap` |
| `LightTexture` | 不存在 | `Lightmap` |
| `GlStateManager` | 存在，但已迁至 `com.mojang.blaze3d.opengl` | 退化为 GL 后端**内部**类，不再是全局状态入口 |
| `RenderLayer` | 同名不同物 | 26.2 的是 `client.renderer.entity.layers.RenderLayer`（实体渲染层），非旧 `RenderLayer` |

Radiance 的核心集成类是 `WorldRendererMixins.java`（393 行），它整个 `ci.cancel()` 掉世界渲染入口自己接管，并靠 `.getGlId()` 把原版 GL 纹理 ID 递给 Vulkan 侧：

```java
// WorldRendererMixins.java:206-211
@Inject(method = "render(Lnet/minecraft/client/util/ObjectAllocator;...Lorg/joml/Matrix4f;Lorg/joml/Matrix4f;)V",
        at = @At("HEAD"), cancellable = true)
public void redirectRender(...) { ... ci.cancel(); }

// :261-270
int overlayTextureID = ((IOverlayTextureExt) overlayTexture).radiance$getTexture().getGlId();
```

**结论**：

- Radiance 的 Java 集成层是 1.21.4 的产物，在 26.2 上**无法编译、无法工作**，必须从零重写。
- 26.2 把渲染器重构成了可插拔后端（`GpuBackend` / `GpuDeviceBackend` / `CommandEncoderBackend` / `RenderPassBackend` / `GpuSurfaceBackend`）。**实现官方 `GpuBackend` 接口**在这条时间线上是唯一可持续的接管方式。
- **MCVR 才是可参考的资产**——它不认识任何 Minecraft 类，与 MC 版本解耦。
- **VulkanMod 不含光追**，不能作为光追参考；它只说明"纯 Java 直调 Vulkan"在 MC 上是可行的。

## 3. 事实清单：参考实现的架构与瓶颈

### 3.1 MCVR 不是"硬编码 pass 列表"，而是 shader-pack 驱动的解释型渲染图

**这是本次调查最重要的结构发现。**

`MainRenderModule` 解析 pack 的 `configs.json`，把 pass 编译成四类变体（`main_render_module.hpp:174-177`）：

```
FullScreenPass / RenderPass / RayTracingPass / ComputePass
```

再用一个**解释执行的"执行程序"**（tinyexpr 表达式 + `if_else` / `pass` / `sharc_update` / `assign` 指令）决定顺序（`main_render_module.cpp:6857-6873`）。

**真正的 pass 顺序写在 JSON 里**：

| pack | 文件数 | 行数 |
|---|---|---|
| `internal/vanilla-pt/configs.json` | 48 | 6,285 |
| `internal/advanced/configs.json` | 128 | 13,711 |

默认加载 `advanced.zip`（`main_render_module.cpp:308-310`），`vanilla-pt.zip` 是 emission 回退包。属性带作者显式标注的 `performance_impact: low|medium|high`，以及 `quality_tier`（默认 **low**）总档位。

**对方案的含义**：要搬的不只是 shader，而是**这套数据驱动渲染图 + 执行程序解释器 + 属性/预算系统**。这既是负担，也是杠杆——一次做好，后续调优不必改 C++。

### 3.2 光追形态：完整 RT pipeline + SBT，零 rayQuery

- 全仓库只有 **2 个** `vkCmdTraceRays*` 调用点：`command.cpp:375`（`vkCmdTraceRaysKHR`）、`command.cpp:383`（`vkCmdTraceRaysIndirectKHR`）
- 上层唯一入口：`MainRenderModule::renderRayTracingPass()`（`main_render_module.cpp:6225-6278`）
- `grep traceRayEXT` 命中 16 处；`grep rayQueryInitializeEXT` 命中 **0 处**

**DispatchRays 次数 = pack 里 `type:"ray_tracing"` 的 pass 数**：advanced **11 次/帧**，vanilla-pt **1 次/帧**（外加 SHARC update 一次）。

RT shader 阶段统计：`.rgen` 12 / `.rchit` 14 / `.rahit` 16 / `.rmiss` 9 = **51 个**。

递归深度：advanced 全部 `1`；vanilla-pt 的 `world` 为 `2`。SBT 实现见 `core/vulkan/sbt.cpp`（有 prefix/suffix hit group、脏区间增量上传）。

### 3.3 几何与加速结构

| 项 | 事实 |
|---|---|
| 图元类型 | 只有 `VK_GEOMETRY_TYPE_TRIANGLES_KHR` + `VK_GEOMETRY_TYPE_INSTANCES_KHR`，**无体素/占用网格/自定义图元** |
| 顶点格式 | `ChunkPBRVertex` **40 字节**；`EntityPBRVertex` **64 字节** |
| 材质位置 | **烘焙进每个顶点**（`textureID` + `packedData` + `colorRGBA8`），无独立材质缓冲 |
| 光照数据 | 独立 `LightData` 数组（7×vec4 = 112B，`chunks.cpp:27-36`），供 ReSTIR 采样，**不参与 BLAS** |
| BLAS 粒度 | 地形 **每区块段一个**；实体每实体一个；Vista 每 part 一个；TLAS **每帧一个** |
| 构建标志 | 区块 `PREFER_FAST_TRACE`（`chunks.cpp:1118`）；实体 `PREFER_FAST_BUILD`（`entities.cpp:2061`） |
| **BLAS update** | **从不使用**。`defineUpdateProperty` 全仓库唯一调用点是 `world_prepare.cpp:600`（给 TLAS） |
| **Compaction** | **零命中** |
| TLAS refit | 仅当"无任何区块渲染版本变化"且 `tlasRefitCount < 32`；超限或版本变化即**强制全量重建**（`world_prepare.cpp:594-637`） |
| 区块实例写入 | **不是 CPU 写的**。CPU 只给 `ChunkRenderRecord`（48B，含 BLAS 设备地址），由 compute `chunk_render_state.comp`（`local_size_x=64`）把所有实例写进 `tlasInstanceBuffer`（`world_prepare.cpp:421-465`） |
| 占位几何 | `definePlaceholderGeometry()`（`as.cpp:70-92`）插入 0 图元退化条目，保证几何条目数与调用方循环一致 |

### 3.4 区块构建调度器（CPU 侧确实是重负载）

`chunks.hpp` / `chunks.cpp` 里有一个完整的 `ChunkBuildScheduler`：

| 机制 | 值 / 位置 |
|---|---|
| 批大小 | `chunkBuildingBatchSize = 8` |
| 总批数 | `chunkBuildingTotalBatches = 4` |
| 工作线程 | `chunkBuildingThreads = 4`（`THREAD_PRIORITY_BELOW_NORMAL` / `setpriority(10)`，`chunks.cpp:198-204`） |
| **每帧上限** | **32 个区块段** |
| 非满批延迟 | 最多等 **3 帧**（`maxPendingBatchFrames_ = 3`） |
| 显存节流 | 压力 ≥ **0.90** 停止调度；≥ **0.85** aggressive 清扫（`chunks.cpp:1940,2647`） |
| staging 缓存 | **256 MiB**（`chunks.cpp:56`）；world_prepare **32 MiB**；entities **128 MiB** |
| 缓冲池 | `ChunkGpuBufferPool` 最佳适配；条目空闲 **120 帧** 后回收 |
| 延迟释放 | `reusableFrameSerial = frameSerial + (swapchain imageCount + 1)` |
| Vista 预算 | 每帧 **8 MiB**（`vista.cpp:480`） |
| 提交方式 | 每批**独立命令缓冲 + 独立 `vkQueueSubmit`** 带自己的 fence |

**关键旁证——优先级路径是死代码**：`publishImportantBuildDataLocked` / `queueImportantBuildUploadsLocked`（`chunks.cpp:2313-2347`）**只有定义、全仓库无调用点**，所以 `importantBLASBuilders_` 恒为空，`submitHighPriorityBLASBuilds` 对区块实为空操作。文档所称"重要区块立即构建"**当前并未生效**。

**串行点**：

- `Chunks` 用**单把递归互斥锁**；渲染线程持锁做元数据上传（`world_prepare.cpp:742-743`），与 Java 线程、4 个工作线程的发布路径共锁
- 批次提交与主帧提交**共用队列锁**（`chunks.cpp:1844-1850`），每帧最多额外 4 次 `vkQueueSubmit`
- `buildLightInfos` 的逐三角形 UV 裁剪**在 Minecraft 线程上同步执行**（`chunks.cpp:2858-2861`）

### 3.5 光追算法与重建

| 项 | vanilla-pt | advanced |
|---|---|---|
| RT pass 数 | 1（52KB uber-`world.rgen`） | 11 |
| 默认 bounce | 4 | 3 |
| ReSTIR | 无 | temporal + spatial + visibility |
| NRD 模式 | `probabilistic` | `half_rate_checkerboard` |
| AS 构建 | `sync` | `deferred` |
| 大气/云 | 简化 | 完整大气介质 + 云 |

**SHARC 辐射缓存（两棵树都用）**：

- `capacityLog2 = 23` → **8,388,608 格**；`sceneScale = 64.0`
- `updateDownsampleFactor = 5`；`resolveFrameStride = 4`（每帧只 resolve 1/4 条目）
- `accumulationFrameNum = 64`；`staleFrameNumMax = 256`
- 查询失败时**回退路径追踪**（`query.glsl:69,89`）——SHARC 的角色是"路追加速器"

**降噪器分工（精确）**：

- 间接光（GI）→ `REBLUR_DIFFUSE_SPECULAR` 或 `REBLUR_DIFFUSE_SPECULAR_SH`
- 直接光 → `RELAX_DIFFUSE_SPECULAR`
- NRD 是 fork `Ljiong201108/NRD` 的 `reblur-sh` 分支；CMake 强制 `REBLUR_PERFORMANCE_MODE=ON`
- **帧率自适应历史长度**：`applyFrameRateTemporalSettings()` 把 FPS clamp 到 `[5,240]`，用 `nrd::GetMaxAccumulatedFrameNum(seconds, fps)` 缩放历史；half-rate 下强制 `atrousIterationNum=2`
- **SVGF 是旁路**：3,848 行、5 级 à-trous、用 FidelityFX 蓝噪声，但**未注册进 `collectWorldModules()`**
- REBLUR 历史 30 帧（fast 6）；RELAX 30/12（fast 6/4）
- 另有轻量 TAA：`temporal_accumulation`，4 输入 1 输出，`alpha=0.12` / 深度阈值 0.05 / 法线 0.9

**运动矢量怎么来的（关键，且与 API 无关）**：

1. 工具函数 `util.glsl:6-12` `computeCameraMotionVector(prevMVP, pixelCenter, motionOrigin)` → **上一帧 MVP 重投影，输出像素单位位移**
2. miss/天空分支（`world.rgen:875`）用 `w=0`（纯旋转）
3. 命中分支（`world.rgen:912-916`）：若 `mainRay.hasPrevScenePos > 0` 则用 `prevScenePos`（实体上一帧场景位置，由 `world_prepare` 上传）
4. **命中点的几何重建**（`advanced/scene/motion.glsl`）：用 previous PBR buffer + previous index buffer + `previousObjectToWorldMatrices` + barycentrics 精确重建上一帧世界位置
5. NRD 收到的 MV 是**像素空间**（`motionVectorScale = {1/width, 1/height, 1.0}`）
6. SVGF 另有虚拟命中点重投影（`svgf/spec_reproject.comp:66-67`）

**jitter**：Halton(3,5) = `coprimes = vec2(3.0F, 5.0F)`，CPU 端写进 UBO（`buffers.cpp:475`），**单源**同时喂相机矩阵、NRD、DLSS、FSR（FSR 需取负）。

**DRS**：无运行时动态分辨率循环。存在的是静态质量比表（FSR/XeSS）与 **NGX `optimalSize` 查询**（DLSS 的 `querySupportedDlssRRInputSizes()`，`dlss_rr_module.cpp:78-84`）——这是唯一的动态成分。

**一个重要的耦合**：`pipeline.cpp:154` 注入 `MCVR_USE_DLSSRR = 0/1`，**advanced 的 ReSTIR 与 froxel 分辨率随之变化**——开 DLSS RR 时 ReSTIR 按全分辨率，关闭时按半分辨率。

| 能力 | 状态 | 关键细节 |
|---|---|---|
| DLSS SR | 已实现 | features `IsHDR` / `MVLowRes` / `AutoExposure`；4 个资源 |
| **DLSS RR** | 已实现 | **8 个 guide buffer**：`COLOR_IN/OUT`、`DIFFUSE_ALBEDO`、`SPECULAR_ALBEDO`、`NORMALROUGHNESS`、`MOTIONVECTOR`、`LINEARDEPTH`、`SPECULAR_HITDISTANCE`；preset `Render_Preset_E` |

### 3.7 编译链

- **运行时 `shaderc`（glslang 前端）编译 GLSL 到 SPIR-V**，`SetTargetEnvironment(vulkan_1_4)`，`optimization_level_performance`，带**磁盘 SPIR-V 缓存**（`shader.cpp:435-444`）
- `shaderKindFromStage()` 显式映射 `shaderc_glsl_raygen_shader / miss / closesthit / anyhit / intersection / callable`
- **不是** HLSL/DXC/slang，**不是**构建期 `glslangValidator`（后者按 README 推测仅服务外部依赖如 NRD/SHARC 的 SPIR-V header 生成）
- shader pack 是 zip，由 minizip-ng 解压，支持用户外部 pack

### 3.8 剖析：682 个埋点，但**全是 CPU 时间**

- 自研 profiler（`profiler.hpp`）：`ScopedScope` RAII + `steady_clock` + 逐帧 **JSON trace**，`MCVR_ENABLE_PROFILER` 开关
- **不是 GPU timestamp query**；GPU 阶段只有 `vk::CommandBuffer::ScopedDebugLabel`（RT 紫、SHARC update 橙、compute 青绿、光栅黄）
- **NRD / SVGF / DLSS 的内部 stage 完全没有埋点**

> **这意味着"GPU 端到底卡在遍历、着色还是降噪"，作者自己的工具链也测不出来。** 这既是他们的盲区，也是 D3D12 + PIX 的切入口。

### 3.9 GL/Vulkan 双 API 互操作（26.2 上不存在的成本）

MCVR 默认 UI 后端是 **OpenGL**。为此 Radiance 有 `OpenGLUiBridge`（631 行），用 `GL_EXT_external_objects_win32` + `GL_EXT_semaphore` 做同纹理双 API 共享：

```
1. 渲染 world，vkCmdBlitImage 把 world blit 进共享 VkImage（导出 memoryHandle + 2 个信号量）
2. surface queue family: mainQueueIndex 转为 VK_QUEUE_FAMILY_EXTERNAL
3. submitFrameCommandBuffers(vulkanReadySemaphore)，交给 GL 的 Minecraft 画 HUD/菜单
4. GL 画完，glSignalSemaphoreEXT(glCompleteSemaphore)
5. MCVR 等 glCompleteSemaphore，blit 回 swapchain image 后 present
```

配套成本：

- 每帧**两次 GPU 信号量往返** + 一次全屏 `glBlitFramebuffer`
- imported NT handle 生命周期管理 + **AMD Windows 驱动 workaround**（`close()` 注释：*"AMD's Windows driver still uses the imported NT handles during semaphore waits. Keep them alive until their GL objects have been destroyed."*）
- resize **100ms 静默期**（`RESIZE_SETTLE_NANOS = 100_000_000L`）+ `glfwWaitEventsTimeout(0.01)` + `GL11.glFinish()`
- 初始化需**让出 GL 上下文**（`releaseContextForVulkanInitialization`）
- 强制 GL 与 Vulkan **同一块 GPU**（`OpenGLDeviceIdentity` 校验）

另有 **Vulkan UI 后端**（`ui_module.cpp` 1,245 行）：一套"拦截 GL 状态机并重放到 Vulkan"的 overlay 层，镜像了 `glScissor` / `glViewport` / `glBlendFuncSeparate` / `glDepthFunc` / `glCullFace` 等全部状态，支持 `registerOverlayDrawShader` 动态编译。

**对 26.2 的含义**：26.2 的 GL 已退化为 `com.mojang.blaze3d.opengl` 包里的一个**可选后端**，官方渲染流程不再依赖 GL 状态机。**单一后端天然没有这套成本**——这是 26.2 平台化带来的结构性红利。

## 4. 瓶颈归属判定

| 归属 | 证据强度 | 是否真瓶颈 | 换 API 能否改善 |
|---|---|---|---|
| **GPU 遍历/着色/降噪** | 强：`PREFER_FAST_TRACE`、每帧全量 TLAS、SHARC(2^23 格) + ReSTIR、REBLUR/RELAX、advanced 11 次 DispatchRays | **主战场** | 不能（同一硬件路径） |
| **CPU 区块几何 + BLAS 构建** | 强：完整 `ChunkBuildScheduler`、每帧 32 段上限、全量重建无 refit、无 compaction、单递归锁 + 队列锁串行 | **是** | 不能 |
| **Java 侧调度** | 中：`ChunkProxy.rebuild/rebuildAll`、`buildLightInfos` 在 MC 线程同步做 UV 裁剪 | 有成本 | 不能 |
| **GL/Vulkan UI 互操作** | 强：双向 blit + 2 个外部信号量 + 队列族转移 + 同 GPU 约束 | 真实但有限 | **唯一确证的结构收益** |

### 被否证的命题

> **"换 D3D12 能把 MCJE 光追性能推到极致"——不成立。**

三条依据：

1. **GPU 侧瓶颈不因 API 改变**：DXR 与 `VK_KHR_ray_tracing` 直通同一硬件 IU，能力对等，天花板由硬件决定。
2. **CPU 侧瓶颈是策略而非 API**：BLAS 全量重建、无 refit、无 compaction、单锁串行——这些在 D3D12 上同样存在，且 D3D12 的显式模型**只增加**样板。
3. **D3D12 唯一可能的独占杠杆已被官方冻结**：**Work Graphs 在 Shader Model 6.10 中被禁用**（保留于 SM 6.8/6.9，原因为"采纳率不足、驱动与硬件尚不够快/省内存"），替代方案 **Work Lists**（`ExecuteIndirect` 扩展）尚未定型。
   - 参考：[VideoCardz 报道](https://videocardz.com/newz/microsoft-disables-work-graphs-in-shader-model-6-10-after-limited-game-adoption)
   - 该功能本可用于"把 BLAS 构建与地形流式更新完全搬到 GPU"，正是 MCJE 最痛处的潜在解法。

### 本仓库已为 D3D12 付过的账

本仓库现有约 8,000 行原生层（三 ring 命令列表、`drawHeap` 622,592 槽分区描述符、BUNDLE 并行录制、四阶段事件状态机、独立渲染线程、延迟结算），**全部是为回收 D3D12 显式模型在栅格化路径上的 CPU 开销**。

而光追路径的特性相反（提交次数极少、GPU 时间占比接近 100%），且 **RT dispatch 不能录进 BUNDLE**——这套基础设施在光追路径上**基本失效**。

## 5. 26.2 上唯一的、确证的平台级杠杆：Java 25 的 Project Panama

### 5.1 事实核对

| 项 | 值 |
|---|---|
| 本仓库编译目标 | `options.release = 25`；`sourceCompatibility/targetCompatibility = VERSION_25` |
| 构建工具链 | `org.gradle.java.home = C:\Program Files\Java\jdk-26-openjdk\jdk-26` |
| FFM API 状态 | **正式特性**（`java.lang.foreign`），JDK 22 定稿，JDK 25 完整可用 |
| MC 26.2 的 Java 要求 | `fabric.mod.json` 声明 `"java": ">=21"`（编译到 25 属自选上限） |

### 5.2 为什么这是"外置库方面有且仅有的优势"

参考实现全部依赖 **JNI**：

| 参考实现 | JNI 相关规模 |
|---|---|
| MCVR | `core/middleware` **1,968 行**，即"Java 类到 JNI 符号"的代理层；构建流程还要求先在 Java checkout 里跑 `./gradlew compileJava` **生成 JNI 头文件**，再 configure CMake（见 MCVR README） |
| 本仓库现状 | `Dx12Native.java` 有 **115 个 `static native` 声明**；6 个 JNI 桥文件共 **2,158 行**（`jni_bridge_p33.cpp` 单文件 954 行） |

JNI 的结构性负担：

- 符号名与包名强耦合（`Java_com_xgdt_dx12_dx12_Dx12Native_*`），**改包名即断链**，且**无编译期检查**——本仓库已有过"注释写旧包名 `com_dx12_dx12`"的实际漂移
- 需要 `javac -h` 生成头文件，Java 与 C++ 构建互相锁定
- 每个调用都要手工 `Get*ArrayRegion` / `NewDirectByteBuffer` / 异常检查
- 句柄传递只能靠 `jlong` = 裸指针，类型不安全
- 回调只能按字符串方法签名查找（本仓库 `Dx12FenceCallback` 按 `(JZ)V` 查找）

### 5.3 Panama 能带来什么

Java FFM API 提供四类原语，恰好覆盖本项目的全部绑定需求：

| Panama 原语 | 替代掉的 JNI 模式 |
|---|---|
| `Linker.downcallHandle(...)` | 所有 `Java_..._dx12CreateTexture` 之类的导出函数 |
| `MemorySegment.reinterpret` + `ValueLayout` | `NewDirectByteBuffer` / `GetDirectBufferAddress` |
| **`MemoryLayout.structLayout`**（group layout） | 手工按字节偏移读写结构体 |
| `Linker.upcallStub(...)` | `GetMethodID` + `CallVoidMethod` 回调 |

**对本项目的具体收益**：

1. **消灭 2,158 行 JNI 桥**：`dx12CreateDevice` 等直接变成 `Linker` 查符号 + 传参，无需 `extern "C"` 导出、无需符号名约定、无需 `javac -h`
2. **消灭手写的小端打包**：本仓库现有 `Dx12Device.buildNativeDesc()` 手工把管线描述按 little-endian 逐字段 `putInt/putU8` 写进 `ByteBuffer`（约 100 行），native 侧再手工解析。改用 **group layout** 后两端共用同一份布局定义，**消除一整类推错偏移/漏算长度的 bug**
3. **消灭字节序陷阱**：本仓库曾因 `NewDirectByteBuffer` 默认 BIG_ENDIAN 导致 UBO 矩阵全垃圾、全黑屏（P26）。Panama 的 `ValueLayout.JAVA_INT.withOrder(LITTLE_ENDIAN)` 是**声明式**的
4. **回调类型安全**：`upcallStub` 绑定 `MethodHandle`，替代按字符串签名查找
5. **构建解耦**：Java 与 C++ 构建不再通过生成的头文件互相锁定；native 侧可以是一个**普通的 C ABI 动态库**，甚至可被其他语言重用

> **这是 26.2 时代相对 MCVR 所处时代的真实代差**：参考实现是 JNI 时代的产物，本仓库可以直接站在 FFM 上，把"Java 与 native"这一层的复杂度整体降一个量级。

### 5.4 需要验证的开放问题

这些**不能假设，必须实测**——它们本身就是实验内容：

- `System.load` / `System.loadLibrary` 在 FFM 方案下是否足够？（FFM 替换的是符号查找与调用，**库加载仍走 `System.load`**，需在实现时确认到具体 JDK 行为，本文不预设结论）
- 高频调用（本仓库每帧数千次 draw）下 `downcallHandle` 的开销是否可接受？
- `Linker.Option.isTrivial()` 等优化选项的适用性与实际效果
- FFM 与官方 `GpuBackend` 调用栈的线程约束是否冲突（本仓库已有独立渲染线程 + worker 池）

## 6. 方案大纲

### 6.1 定位重述

> **在 MC 26.2 的官方可插拔后端架构上，用 Java 25 FFM + 单一现代图形 API，搭一个实验性渲染后端；以"能不能做、代价多大、瓶颈在哪"为研究问题，性能只是其中一个探究方向。**

因此方案要在**每一层明确"实验变量"**，而不是追求一个可发布的模组。

### 6.2 分层设计

```
L4  实验层：光追 / 网格着色器 / 时序重建 / 超分 / 帧生成
     数据驱动渲染图（借鉴 MCVR 的 shader-pack 思路）
     每个能力一个独立开关，可单独启用以做 A/B

L3  管线层：PSO / 根签名或 pipeline layout / 描述符 / SBT
     必须上 DXC（RT 需要 SM6.x DXIL）——若选 D3D12

L2  抽象层：重投影与时序基础设施（一次做好，多处复用）
     jitter 单源 / 上一帧 viewProj / 历史缓冲 / 运动矢量

L1  绑定层：Java 25 FFM 替换 JNI
     group layout 定义所有跨语言结构体
     纯 C ABI 动态库（无 JNI 导出）

L0  宿主层：官方 GpuBackend 接口族
     Dx12Backend / Dx12Device / CommandEncoder / RenderPass
     26.2 的 FrameGraph（有 persistent target 与资源生命周期）
```

### 6.3 阶段划分

#### 阶段 0：绑定层换代

**实验问题**：FFM 能不能扛住高频调用？

- 用 FFM 重写现有 `Dx12Native` 的 115 个 native 声明
- 用 **group layout** 重写 `buildNativeDesc` 的管线描述（消除 §5.3-2/3 两类 bug）
- 用 `upcallStub` 替换 `Dx12FenceCallback`
- **实验指标**：`downcallHandle` 在数千次/帧下的实际开销 vs JNI；`isTrivial` 等选项的效果
- **产出**：一份"FFM vs JNI 在本工作负载下的实测报告"

#### 阶段 1：时序基础设施（一次投入，三处受益）

这是**所有时序技术（TAA、超分、光追去噪）的公共前置层**，且**与图形 API 无关**——是纯收益。

| 件 | 现状（本仓库） | 要做的 |
|---|---|---|
| jitter | 无 | 借鉴 MCVR 单源方案：Halton(3,5) 写进 UBO，同时喂相机矩阵与重建器；注入点候选 `GameRenderer.java:579` 的 `setProjectionMatrix(...)` 或 `ProjectionMatrixBuffer#writeBuffer` |
| 上一帧 viewProj | 无 | 在投影矩阵构造时保存（那里才有未 jitter 的完整矩阵） |
| 历史缓冲 | 无 | 26.2 的 `PostChainConfig.InternalTarget` **已有 `persistent` 标志**，`FrameGraphBuilder.createInternal` + `readsAndWrites` 可承载 |
| 运动矢量 | 无 | **两级路线**：一是先做深度重投影（零侵入，只对静态几何正确）；二是再借鉴 MCVR 的**命中点几何重建**（需保留上一帧顶点/索引缓冲地址 + barycentrics） |
| TAA resolve | 无 | **不能写成 compute**——26.2 官方 API 没有 compute dispatch（`DeviceFeatures`/`DeviceLimits` 里无相关字段，`blaze3d` 全目录 `dispatch`/`ComputePipeline` 零命中）。只能写成全屏像素着色器 + 手工模拟邻域钳制 |

**实验指标**：深度重投影 vs 命中点重建的鬼影程度与代价；TAA 在体素世界（重投影精确度高）能省多少采样。

#### 阶段 2：加速结构

**实验问题**：体素世界的 BLAS 策略应该是什么？

这是**唯一可能与参考实现做出差异**的地方——MCVR 在这里有明显未开发空间：

| 可实验项 | MCVR 现状 | 实验假设 |
|---|---|---|
| BLAS refit vs 全量重建 | 从不 refit | 方块编辑多为局部改动，refit 可能大幅降低 CPU 成本 |
| AS compaction | 零命中 | 无压缩 + 90% 显存节流等于自伤；压缩后可能解除节流 |
| 加速结构形态 | 纯三角形 BLAS | 体素占用网格 / 稀疏结构 + 自定义遍历，避开每帧重建 |
| 优先级调度 | `important` 路径是**死代码** | 让"重要区块立即构建"真正生效 |
| 上传路径 | 逐三角形 UV 裁剪在 MC 线程同步 | 移出主线程 |

**同时注意**：26.2 的区块重建走 `SectionRenderDispatcher`，重建在 worker 线程池里跑，时机受 `compileSections` / `uploadTerrainBuffersToGpu` 调度——**撞上 MC 的区块生命周期与多线程模型是这个阶段的主要风险**。

#### 阶段 3：光追管线

**实验问题**：SBT 管线的移植代价有多大？

- 参考 MCVR 的 pass 结构（advanced 的 11 个 RT pass + phase flip 乒乓）
- 用**数据驱动的渲染图**复现（借鉴 `configs.json` 思路），而非硬编码 pass 列表
- **必须新建 DXC/SM6.x 工具链**（现有 `D3DCompile(vs_5_1/ps_5_1)` 出不来 DXIL）
- SBT 是 DXR 最易出错处：Vulkan 与 D3D12 的记录步长/对齐/`InstanceContributionToHitGroupIndex` 语义不同，**不能照抄**
- 降噪**优先接 NRD 的 D3D12 后端**（NVIDIA 官方同时提供 Vulkan 与 D3D12），而非自研

#### 阶段 4：超分与帧生成

- 接口需求与阶段 1 的辅助缓冲**完全重合**（jitter + MV + 深度 + 分辨率解耦）
- **最大拦路石是 MC 的架构假设**：`MainTarget` / `RenderTarget.resize` / GUI 布局判定全部以窗口尺寸为源。要做"从低分辨率升采样"，需要把整条主渲染链 + 后处理链 + GUI 合成从"window size"改成"render size + upscale"，且 GUI 必须在最终分辨率上单独渲染
- DLSS/FSR/XeSS 均需原生 COM 句柄，FFM 可直接取（现有 `dx12GetDeviceHandle` / `dx12GetQueueHandle` 已暴露）

### 6.4 与参考实现的差异表（必须记住的）

| 维度 | MCVR / Radiance | 本方案（26.2） |
|---|---|---|
| 集成方式 | `ci.cancel()` 掉 `WorldRenderer.render`，自建渲染器 | 实现官方 `GpuBackend` 接口族 |
| MC 版本 | 1.21.4 | **26.2（渲染器已重构）** |
| Java 与 native | JNI + `javac -h` 头文件生成 | **Java 25 FFM（Panama）** |
| UI 合成 | GL 画 UI + Vulkan 合成世界（跨 API 桥） | **单一后端，无桥** |
| 渲染图 | `configs.json` 解释执行 | 待定：可借鉴，但 26.2 已有官方 `FrameGraphBuilder` |
| shader 链 | 运行时 shaderc，GLSL 到 SPIR-V | 现有 GLSL 到 spvc 到 HLSL 到 DXBC，**需升级到 SM6.x/DXC** |
| 光追 | 完整 SBT，零 rayQuery | 待建 |
| 降噪 | NRD(REBLUR/RELAX) + 旁路 SVGF | **优先接 NRD 的 D3D12 后端** |
| 剖析 | 682 个 CPU 埋点，**无 GPU timestamp** | **PIX 的 GPU 时间线**（这是相对优势） |
| 参考实现的未开发空间 | BLAS 无 refit、无 compaction、优先级死代码、单锁串行 | 可在方案中直接规避 |

### 6.5 本方案的实验变量（研究问题清单）

写方案的目的是**能回答这些问题**，建议每个问题都设计成可测量：

1. **Panama 的代价**：FFM `downcallHandle` 在数千次/帧下 vs JNI，差多少？`isTrivial` 有用吗？
2. **重投影精度**：体素世界的深度重投影 vs 光追命中点几何重建，鬼影差多少？代价差多少？
3. **时序收益上限**：MCJE 的静态体素场景特性，能让每像素采样数降到多低？
4. **BLAS 策略**：refit vs 全量重建的实际 CPU 成本比；compaction 能省多少显存、能否解除 90% 节流？
5. **加速结构形态**：三角形 BLAS vs 体素结构 + 自定义遍历，在区块高频重建下的总成本？
6. **GPU 瓶颈归因**（参考实现测不出来的）：遍历 / 着色 / 降噪 各占多少？用 PIX 测量
7. **单一后端 vs 双 API**：26.2 的架构红利到底值多少 ms/帧？（对比 MCVR 的跨 API 桥）
8. **网格着色器在体素世界值不值**：meshlet 级剔除 vs MC 已有 section 级遮挡图，净收益？

### 6.6 风险登记

| 风险 | 说明 | 缓解 |
|---|---|---|
| **MC 版本演进** | 26.2 的重构是新的，Radiance 那条路已因版本升级而死；本方案同样有这个风险 | 尽量贴官方接口，少用 mixin 打洞；打洞处集中记录 |
| **26.2 无 compute API** | 官方 `DeviceFeatures`/`DeviceLimits` 无 compute 相关字段，`blaze3d` 全目录 `dispatch`/`ComputePipeline` **零命中** | 需要 compute 的能力（GPU 光追实例写入、降噪）必须绕开官方接口在原生层自开通道 |
| **DXC 工具链新建** | RT 需要 SM6.5+ DXIL | 早做，且作为独立阶段验证 |
| **分辨率解耦** | 超分的前置，侵袭性最大 | 放到最后；先只做 TAA（不需解耦） |
| **体素几何的 BLAS 高频重建** | 可能吃掉所有收益 | 阶段 2 的核心研究问题 |
| **纯 Java 侧的可行性未知** | VulkanMod 证明纯 Java 可行，但**无光追**；MCVR 走 C++ | 保留 C++/FFM 路线为主 |

## 8. 下一步建议

按"实验价值 / 成本"排序：

1. **阶段 0（FFM 换代）** 成本最低、结论最确定、且**无论最终选哪个图形 API 都要做**——建议先做。
2. **阶段 1（时序基础设施）** 是 TAA、超分、去噪三者的公共前置，且与 API 无关——**纯收益，建议紧随**。
3. **阶段 2（加速结构）** 是唯一可能做出真实差异的地方，也是风险最集中处——建议先做**只读的可行性验证**（体素结构 vs 三角形 BLAS 的构建成本模型），再决定是否投入。
4. **阶段 3/4（光追管线、超分）** 规模最大，建议在 1、2 出结论后再决策。

**关于图形 API 的选择**：本文档不做推荐。§4 已论证"换 API 不是性能手段"；是否选 D3D12，建议作为一个**独立的实验变量**（工具链、FFM 亲和度、驱动一致性、PIX 可用性）来评估，而不是绑在光追方案上一起决策。
